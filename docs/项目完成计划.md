## 4. 技术路线：保持简单，结果要能解释

### 共享数据处理：A 负责

统一产出结构表、基因表、样本列表和窗口读取函数。默认把 10 bp counts 按 **100 bp** 聚合为工作数据，保留原始文件；从工作数据取 **24 kb 窗口，缩放为 128×128**。这一窗口可容纳现有标注中跨度最大的结构，模型规模也较小。先看三类示例，若 CHIN 细节明显丢失，再补 8 kb 视角；不预先搭多尺度模型。

基础归一化采用测序深度归一化；模型与形态分析再用按基因组距离计算的 O/E（观察接触量除以同距离的平均接触量），配合 `log1p` 和统一截断范围。这些是本组的初始设计选择，先在少量窗口上检查效果。不要为本课程额外实现一套复杂校正方法。

形态用的标准化结果与强度比较用的数据分别保留：任务四和接触强度轨道不能使用“每个窗口各自归一到同一均值”的数据，否则可能抹去真实强弱变化。处理零背景和无效 bin，统计忽略的像素即可。

基因组是环状的，窗口跨起点时做首尾拼接；距离背景考虑环状距离。所有模块复用这一个窗口函数。输出坐标记录原始基因组位置，跨起点窗口附两个分段区间。

### 任务一：B 负责

使用 2—3 个卷积模块的小 CNN，直接读数值矩阵，训练三分类。用类别权重处理 68 / 250 / 26 的不均衡；以验证集选择停止轮次。

按基因组位置分组后划分训练、验证、测试集，目标比例约 70% / 15% / 15%，优先保证三类在各集合有样本。同一结构的重复、增强样本和相互重叠的窗口不能跨集合。数据量较少，不必追求精确比例。

提交准确率、混淆矩阵和 Macro-F1；加一个简单的多数类或线性分类基线，帮助解释模型是否学到了有用信息。每类选 2—3 个样本展示梯度显著性图或 Grad-CAM，并展示少量失败案例。固定一个主随机种子，结果异常再补一次运行，不安排大规模重复实验。

### 任务二：C 主责，B 做跨重复检查

1. 在 WT rep1 上沿全基因组滑窗，初始步长 1 kb。用排除已知结构后的背景窗口训练小型卷积自编码器。
2. 用形态归一化后的重建误差给窗口打分，同时保留简单接触强度分数作对照，检查候选是否只是在挑高密度区域。
3. 检查已知结构召回情况，导出每类召回统计；用自编码器隐向量表征候选，与已知结构和随机背景共同做 PCA 展示，并用简单分类对照检查表征区分能力。
4. 在 PCA 后的表征上对候选与已知参考共同聚类，默认 DBSCAN。只试少量参数；输出成员、中心和代表热图。先合并同一基因组区域的重复窗口，不能把一个位置的五个相邻窗口当成五个成员。
5. 初始“疑似新结构簇”规则为：至少 5 个独立候选位置、簇内没有已知参考成员、候选区间不与已知结构重叠；DBSCAN 的噪声标签不算一个簇。再检查它是否只是已知形态的变体，并在报告中说明这一规则是本组约定。
6. 在 WT rep2 相同位置提取窗口，计算 O/E 上三角的相关性并并排画图；掩去主对角线及无效像素，用已知结构和随机背景作参照。打分和参数调整主要使用 rep1，rep2 用于最后复现检查。

分类器可作为已知结构筛查的辅助证据，但三分类 softmax 低置信度不能直接作为“新结构”的证明。不给复现相关性预设一个宣称普适的硬阈值；在看过已知结构与随机背景的对照后，固定本组规则并报告所有候选的指标。

**不承诺一定发现生物学上的新结构。** 实践方案第 10 页明确允许以正确复现已知结构作为任务二最低完成度。若没有可信的新簇，保留完整发现流程、已知结构召回和排除案例，并如实说明结论。

### 任务三：C 负责

先画一张 10 kb 区间图，经组内确认后批量输出 465 张。四个面板依次为：三个条件的接触强度曲线与灰色基线、条件平均信号、蓝色基因轨道、橙色 CHIN/OPCID 结构轨道。共享横轴，带图例、基因/结构名称和坐标。

接触强度统一定义为每个 bin 的有效接触总量按该样本总接触量缩放，必要时开平方显示；先对每个重复归一化，再按条件取均值。稀疏上三角计数转成 bin 接触总量时，非对角项累加到两个端点，避免漏算。报告选 3—5 张典型区间图，其余作为完整输出。

### 选做任务四：A 负责

以 WT 为对照，比较 ΔstpA、ΔhnsΔstpA，主要在 344 个已知结构和最终保留的候选位置上分析。使用相同区间、掩码和归一化方法，输出归一化接触强度的 log2 fold change，辅以 O/E 形态差异和并排热图。

各条件保留两个重复，检查它们相对 WT 均值的改变方向是否一致；用 WT rep1 与 rep2 的差异作为背景参照。选 5—10 个清楚的改变或稳定案例，说明哪类结构增强、减弱或变化不明显。两个重复足够做课程层面的描述性比较，不另设复杂显著性检验。

如果没有清晰减弱的例子，按结果报告，不挑图强行支持预设结论。ΔhnsΔstpA 同时改变两个因素，对它的观察不能直接全部归因于 H-NS。

## 6. GitHub 协作方式

只需要一个仓库、一个 `main`、12 个 issue 和普通 PR，不额外搭服务、数据库或自动化平台。

1. 按 `GitHub任务清单.md` 链接的正式 issue 执行；表中的 `P01` 等保留为计划编号，GitHub 编号以链接为准。A 统筹任务分配。
2. 每个普通 issue 对应一个分支和一个 PR；共同报告 issue 允许三人分别提交自己章节的 PR。分支如 `feat/12-classifier`，其中数字换成实际 issue 号。
3. PR 写清做了什么、运行命令和一张代表图/一组指标；关联 `Closes #实际编号`。共享报告的子 PR 先用 `Refs #实际编号`，最后完成时再关闭 issue。关闭关键词在合入默认分支时才按 GitHub 规则生效。[GitHub 官方说明](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)
4. 由一名其他成员检查输入输出、能否运行、结果是否合理，通常 5—10 分钟；不要求两人都审核。A 的 PR 主要由 B 看，B 的由 C 看，C 的由 A 看。
5. 每人完成或卡住时在 issue 留一句进度；只在 D2、D7、D11 做短同步，不安排每日长会。
6. AI agent 可以写实现和文档，但负责人自己看一遍代表输出，确认数值、坐标、图和报告说法相符。

仓库提交脚本、小配置、整理后的标注、小型结果表和代表图。原始 `.cool`、`.tar`、中间缓存与大批量图输出通过数据目录或共享存储传递，并用 `.gitignore` 排除；README 写清原文件来源、放置位置和运行顺序。模型权重保留在最终实验包或共享位置。此项目无需引入 Git LFS、DVC、复杂 CI 或测试框架。

建议只有几个可顺序执行的入口，例如 `prepare_data.py`、`train_classifier.py`、`discover.py`、`compare_conditions.py`、`plot_tracks.py`，以及一份小配置；这些是计划中的名称，不代表已实现。长时间的完整训练不必成为每次 PR 的检查条件，小样本执行成功并提供完整实验结果即可。
